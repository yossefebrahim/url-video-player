# Video-player & cast lifecycle audit

> **Generated by** an 8-dimension multi-agent audit with 2-lens adversarial
> verification (67 agents). Findings below are those that survived verification.
>
> **Remediation status (applied 2026-07-06, same session):**
> - **All 5 P1 fixed:** SSRF host-allowlist in `HlsCastProxy`; proxy teardown on
>   the `connectAndCast` throw path *and* at connect entry; `_ensureParsed`
>   clears its memo on a failed fetch; `_fetch` rejects non-2xx and times out a
>   stalled body.
> - **6 of 8 P2 fixed:** ref-counted `WakelockCoordinator` shared by player +
>   cast; `VideoPlayerView` releases the wakelock on `exception`/`finished`;
>   passive cast-disconnect no longer autoplays the local player from 0:00;
>   `/beacon` body cap; `/init`·`/seg` index validation; encrypted `EXT-X-MAP`

>   DASH still casts to origin and falls back locally after a ~15 s honest error

> - **3 of 7 P3 fixed:** malformed `EXT-X-KEY` resets key state; receiver beacon
>   only falls back to a LAN host and re-queues dropped lines; `categoryForCast`
>   guards a blank appId. Remaining P3s (unbounded key cache, `decryptAes128Cbc`

## Executive summary

The player and cast lifecycle machinery is broadly sound: the generation guard, the deliberate no-AnimatedSwitcher double-playback fix, the honest cast-failure fallback, and the proxy's core validation all hold up under scrutiny. However, the newly-rewritten cast proxy stack carries real defects — **21 findings survived verification: 6 P1, 8 P2, 7 P3** (three lower-severity findings share root causes with higher ones and are merged below). The single most important fix is the **open SSRF relay in the LAN proxy** (`cast_proxy_server.dart:113`): any device on a hostile shared Wi-Fi can drive the phone to fetch arbitrary internal/metadata hosts with the stream's headers attached. Close behind it are two proxy-lifecycle leaks in `cast_service.dart` that orphan a bound `HttpServer` and permanently pin the wakelock when a cast fails after a proxy is adopted, and a memoisation bug that bricks a whole DASH session on one transient network hiccup. These are all reachable in real usage, not theoretical.

## Findings

### [P1] lib/services/cast_proxy_server.dart:113 — Open SSRF relay: proxy fetches any client-supplied URL with origin headers attached

On a hostile shared network (public/hotel Wi-Fi — a target scenario, since users paste `http://` URLs), any LAN device can hit `http://phone:port/seg.ts?u=<b64url>` where `u` decodes (via `HlsRewriter.decodeUrl`, a bare base64url decode with zero scheme/host validation) to `http://169.254.169.254/`, the router admin page, or any internal host. The proxy binds `anyIPv4` with wildcard CORS, fetches the URL from the phone's network position, returns the body cross-origin, and `_fetch` copies `upstreamHeaders` (the stream's User-Agent) onto the attacker-chosen request — an unauthenticated SSRF / anonymizing relay. **Fix:** key the segment/playlist/key endpoints to a per-session allowlist of resolved base host(s) captured at `start()`, reject any decoded `u=` whose scheme/host isn't in it, and never forward `upstreamHeaders` to off-allowlist hosts. Optionally bind to the specific LAN address and require an unguessable per-session path token. (Note: only User-Agent is forwarded — `VideoItem` carries no auth header — and the window is limited to an active cast session; the SSRF and UA leak are nonetheless real.)

### [P1] lib/services/cast_service.dart:165 — connectAndCast catch block never stops an already-adopted proxy

When a live-HLS or CENC-DASH cast reaches `_adoptProxy` (which starts the proxy `HttpServer`, sets `_proxy`, and calls `WakelockPlus.enable()`), then `loadMedia` (line 142) or `_awaitPlaybackStarted` (line 152) throws, execution jumps to the catch at line 165 which only sets `CastPhase.error` and returns false. `_stopProxy()` is never called, so the bound `HttpServer` + open `HttpClient` keep running and the wakelock stays enabled. This is asymmetric with the graceful non-throwing failure path (152–160), which does call `_endSessionQuietly()` → `_stopProxy()`. Because phase is `error` (not active), a later session-drop event won't clean it up either. **Fix:** wrap the media/load/await section in try/finally, or add `await _stopProxy();` inside the catch before setting the error state, so any exception after a proxy is adopted tears it down and releases the wakelock.

### [P1] lib/services/cast_service.dart:130 — New cast attempt leaks a prior live proxy if it aborts before _prepareMedia

`connectAndCast` only tears down a pre-existing proxy inside `_prepareMedia` (`await _stopProxy()` at line 186), which runs *after* `startSessionWithDevice` and `_awaitConnected`. The reachable path: a prior cast adopts a proxy, then `loadMedia` throws → catch at 165 leaves the proxy orphaned while `isConnected` stays false, so the device picker is reachable again; the user retries, and if that attempt aborts before line 186 (`startSessionWithDevice` returns false, or `_awaitConnected` times out), the first session's proxy `HttpServer` and wakelock leak for the rest of the app's life. **Fix:** call `await _stopProxy();` at the very start of `connectAndCast`, before `startSessionWithDevice`, so any pre-existing proxy is torn down regardless of how far the new connect gets. (This and the P1 above share the same root cause — proxy teardown is not guaranteed on failure paths — and one thorough fix, stopping the proxy on every entry and every exception, closes both.)

### [P1] lib/services/cast_proxy_server.dart:217 — _ensureParsed caches the in-flight future without resetting on failure, permanently bricking the DASH session

`_ensureParsed() => _parsing ??= _doParse()` memoises the one-time manifest-fetch future. If the first `_fetch(upstreamMpdUrl)` fails transiently (DNS hiccup, momentary Wi-Fi drop, or the 15s `connectionTimeout`), that future completes with an error and is never cleared. Every later `/manifest.mpd`, `/init`, `/seg` request re-hits `_parsing != null`, so `??=` returns the same rejected future → 502 forever. A fresh `CastProxyServer` is created per session but the receiver keeps polling this poisoned instance, so the cast is dead until the user tears down and re-initiates. **Fix:** don't cache a failed future — null `_parsing` in a catch before rethrowing, e.g. `_parsing ??= _doParse().catchError((e){ _parsing = null; throw e; })`. (Note: an upstream 503 does *not* poison it, because `_fetch` ignores status codes — see next finding — but DNS/Wi-Fi/timeout triggers are sufficient.)

### [P1] lib/services/cast_proxy_server.dart:117 — _fetch ignores resp.statusCode, serving upstream error pages as media

`_fetch` reads and returns the response body with no check of `resp.statusCode`. For a rolling live DASH/HLS window, an expired CDN token (302 → 403) or an aged-out segment (404) returns an HTML/JSON error body that flows through as "success": `_rewriteManifest` runs its regexes over the error page (no `SegmentTemplate` matches → empty `_reps` → a content-free 200 manifest), and `/init`/`/seg` hand the error bytes to the CENC box-walker, which serves untouched garbage as `video/mp4`. The receiver gets corrupt/empty media with a 200 instead of a status it could react to, and `/beacon` shows only opaque player errors. **Fix:** after `req.close()`, check `resp.statusCode`; if not 2xx, drain/abort and throw (or propagate the status) so `_dispatch` returns a matching error code.

### [P2] lib/widgets/video_player_view.dart:156 — Wakelock enabled on 'initialized' is never released when the stream errors after initializing

`WakelockPlus.enable()` fires on the `initialized` event (line 156); `WakelockPlus.disable()` lives only in `_teardown()` (line 186), reached via `_retry()`, the UA-change branch of `didUpdateWidget`, and `dispose()`. The `addEventsListener` block handles only `initialized`/`progress` — no `exception`/`finished` case. When a live stream initializes, plays, then dies mid-playback, better_player renders `_ErrorBox` via its internal `errorBuilder` *inside* the live `BetterPlayer` subtree without touching this State or calling `_teardown()`, so the app-level wakelock stays held on the error screen, draining battery until the user hits Retry or leaves. **Fix:** handle `BetterPlayerEventType.exception`/`finished` in the events listener and call `WakelockPlus.disable()` (guarded by `_isStale(gen)`) when playback stops or errors after having been enabled.

### [P2] lib/screens/home_screen.dart:425 — After a passive Cast disconnect the local player silently remounts and autoplays from zero

`_current` is never reset to null, and casting requires it non-null. On a passive TV drop, `CastService._onSessionChanged` sets `CastPhase.idle` and bumps `passiveDisconnects`; `_playerStage` rebuilds with `castState.isConnected` now false and `_current` still the cast item, so it constructs a fresh `VideoPlayerView` keyed by `_current!.url` with `autoPlay: true` and no `startAt` — the phone starts blaring the same video from 0:00 while the user sees only a "Cast disconnected." snackbar. The cast position is also lost (never fed back). **Fix:** on passive disconnect decide the fallback explicitly — keep the idle poster (clear `_current` or track a "was casting" flag so the player doesn't auto-remount), or remount paused and seek to the last known position; at minimum, do not auto-start local playback from zero without user intent.

### [P2] lib/services/cast_proxy_server.dart:38 — Upstream fetches have no response/idle deadline, so a stalled body hangs the request forever

The shared `HttpClient` sets only `connectionTimeout` (15s), which bounds connection establishment, not the body drain. `_fetch` does `await for (final c in resp)` with no `.timeout(...)` and no idle guard. A flaky CDN edge that completes the TCP handshake (so `connectionTimeout` never trips) then stalls mid-segment leaves the `await for` blocked indefinitely; that request never responds, the receiver's segment fetch hangs, and the upstream socket leaks. On live HLS this recurs per-segment and stalled fetches accumulate. **Fix:** apply a per-request deadline — wrap the drain in `resp.timeout(Duration(seconds: 20))` (or `Future.any` with a timer) and, on timeout, abort the socket and return 504 so the receiver can retry the next segment.

### [P2] lib/services/cast_service.dart:223 — UA-gated unencrypted DASH (and progressive) is cast to origin, where the receiver can't apply the User-Agent

`needsHlsProxy` only proxies UA-gated HLS. A plain unencrypted DASH manifest served only to a specific User-Agent skips the CENC-DASH proxy branch (`isEncrypted` is false), is not `obfuscated`, and isn't HLS — so it falls through to `CastMediaMapper.mediaInfoFor`, which sets `contentId` to the origin `.mpd` and stuffs the UA into `customData` (ignored by the default receiver). The Chromecast fetches the manifest with no UA, the CDN rejects it, and `_awaitPlaybackStarted` times out after 15s. Same gap for UA-gated progressive MP4/TS. (This is a documented Phase-1 limitation and does fall back to local playback with an honest error, so impact is bounded.) **Fix:** route any UA-gated stream (`headers.isNotEmpty`) the receiver can't fetch itself through a proxy regardless of container — allow `CastProxyServer` to run with a pass-through no-op decryptor when headers are present but the stream is unencrypted; at minimum, detect `headers.isNotEmpty` on a non-proxied stream and surface the "needs custom User-Agent, not supported" error up front instead of waiting for a 15s timeout.

### [P2] lib/services/hls_rewriter.dart:76 — AES-128 #EXT-X-MAP init segment with no explicit IV is emitted with no key/IV and served still-encrypted

In the `#EXT-X-MAP` branch, `_segmentRef` is called with `iv: keyIv` where `keyIv` is null (no explicit IV attr) — unlike the segment branch, which derives an IV from the media sequence. `_segmentRef` only appends `&k=`/`&iv=` when `iv != null`, so the MAP becomes a bare `seg.ts?u=<init.mp4>`; the proxy's `_serveSegment` sees no key params and returns the AES-128-encrypted init segment verbatim. The receiver gets a corrupt moov/init and the fMP4 variant fails to initialize. The class comment even notes the MAP needs an explicit IV, but nothing warns or falls back. **Fix:** when `keyUri != null` but no usable IV exists for the MAP, derive an IV per the documented convention so the proxy can decrypt it, or route the MAP through pass-through and keep the `#EXT-X-KEY` line — do not emit a bare `seg.ts?u=` for an encrypted init segment.

### [P2] lib/services/cast_proxy_server.dart:92 — /beacon reads the entire POST body with no size cap

`_handleBeacon` does `utf8.decodeStream(req.cast<List<int>>())`, buffering the whole body into a String before the 200-line `receiverLog` trim (which bounds only retained lines, not the transient read). Since the server binds `anyIPv4` with wildcard CORS and no auth on `/beacon`, any Wi-Fi peer — or a runaway receiver POSTing its whole log — can drive a multi-MB transient allocation. **Fix:** reject when `req.contentLength` exceeds a small cap, or accumulate bytes and abort once a threshold (e.g. 64 KiB) is exceeded, before decoding. (Gating `/beacon` to the session origin as part of the SSRF fix covers the exposure too.)

### [P2] lib/services/cast_proxy_server.dart:232 — Client-supplied /init and /seg path indices are parsed and indexed without validation

`/init/99` → `_reps[99]` RangeError; `/init/abc` → `int.parse` FormatException; `/seg/0` (missing second part) → `parts[1]` RangeError. `_dispatch` converts these to a 502 (no crash), but the index is never bounds-checked against `_reps.length` and split parts aren't length-checked, so a stale/invalid request from a probing LAN client or a benign receiver retry gets an opaque 502 (falsely implicating upstream) instead of a clean 404. **Fix:** parse with `int.tryParse`, check the split has 2 parts, and bounds-check `idx` against `_reps.length`, returning 404 for anything invalid before indexing.

### [P2] lib/services/cast_service.dart:255 — Wakelock is a non-refcounted global flag shared and fought over by VideoPlayerView and CastService

`WakelockPlus.enable()/disable()` toggle one process-global flag with no ref-count. `VideoPlayerView` enables on `initialized` (video_player_view.dart:156) and disables in `_teardown` (186); `CastService` enables in `_adoptProxy` (255) and disables in `_stopProxy` (268). On the ordinary connecting-before-adopt path the ordering is benign, but the shared flag means any `VideoPlayerView` teardown/dispose that fires while a proxy is already alive (a later rebuild, backgrounding, or a genuinely orphaned controller) silently disables the proxy's wakelock — the exact Doze stall the proxy wakelock exists to prevent — because neither component ref-counts its claim. **Fix:** route all wakelock enable/disable through a single ref-counted coordinator (`acquire()`/`release()`, enabling on first acquire and disabling on last release) shared by both, instead of both calling the global API directly.

### [P3] lib/services/cast_proxy_server.dart:350 — Byte-range HLS (#EXT-X-BYTERANGE) is unsupported and silently mis-decrypted

The rewriter preserves `#EXT-X-BYTERANGE` lines verbatim but rewrites every entry (even several pointing at one file) to the same `seg.ts?u=<full-url>`. `_serveSegment` ignores Range, always fetches the whole file, never forwards a Range header upstream, and under AES-128 decrypts the whole file with a per-entry sequence IV — wrong for a sub-range (CBC needs the preceding ciphertext block and block alignment). Clear byte-range streams re-download the full file per sub-range; encrypted ones get garbage. The targeted obfuscated channels use full-file TS segments, so this is uncommon here. **Fix:** detect `#EXT-X-BYTERANGE` and either forward the receiver's Range upstream and serve the decrypted block-aligned slice, or explicitly gate byte-range HLS to local playback; at minimum document it as unsupported alongside the other scoped limits.

### [P3] lib/services/cast_proxy_server.dart:307 — Unbounded, never-evicted AES key cache

`_keys[keyUrl] ??= await _fetchKey(keyUrl)` adds a permanent entry per distinct key URL and is only reclaimed when the `HlsCastProxy` is disposed. Live channels that rotate `#EXT-X-KEY` accumulate one entry (16-byte value plus a potentially long signed CDN URL string) per rotation over a multi-hour session. Values are tiny (order-of-MB total), so this is hygiene, not a crash. **Fix:** bound the cache with an LRU capped at a few dozen entries, or key it by a rotating window — keys for segments that scrolled out of the live window are never requested again.

### [P3] lib/services/hls_rewriter.dart:56 — Malformed AES-128 #EXT-X-KEY with no URI leaves stale key state active

An `#EXT-X-KEY:METHOD=AES-128` line lacking `URI=` fails the guard on line 56 and falls into the SAMPLE-AES `else` branch, which writes the line verbatim but never resets `keyUri`/`keyIv`. Subsequent segments keep the previously-active key and get `&k=`/`&iv=` for the wrong key, decrypting to garbage instead of failing cleanly. Only reachable with a spec-violating playlist (RFC 8216 makes URI required for any non-NONE method). **Fix:** in the AES-128 branch, treat a missing URI as a reset (`keyUri = null`) so the proxy doesn't apply a stale key.

### [P3] lib/services/cast_proxy_server.dart:389 — decryptAes128Cbc throws on any non-16-aligned ciphertext, turning a short segment into a 502

A truncated/short/empty `.ts` segment (non-multiple-of-16 length) makes `decryptAes128Cbc` throw `StateError`; `_dispatch` turns it into a 502 with the cause only in debug logs. In practice AES-128-CBC segments are always block-aligned, so a non-aligned length signals genuinely corrupt data, and a 502 on one segment is itself the standard recoverable signal an HLS player retries past — so this is closer to correct defensive validation than a defect. **Fix (optional):** treat a non-aligned/empty live segment as a soft failure (log and surface a distinct status the receiver can advance past) rather than a generic 502.

### [P3] cast_receiver/index.html:88 — Absent customData.beacon makes the receiver POST diagnostics to the third-party CDN

On the direct (`mediaInfoFor`) cast path for plain `http://` HLS/MP4, `customData` has no `beacon` key, so the LOAD interceptor's `else if (/^http:\/\//.test(url))` branch fires and `beaconUrl` becomes `new URL('/beacon', contentId)` = `http://<cdn-host>/beacon`. Every log line (device caps, codec probe, player state, error JSON) is POSTed to the CDN's `/beacon`, leaking receiver diagnostics to an unrelated origin, generating 404 noise, and denying the phone the telemetry for exactly the streams that most need debugging. (Playback is unaffected; https origins don't trigger it.) **Fix:** only derive a beacon target from `contentId` when the origin is an RFC1918/LAN host, or drop the origin fallback and require `customData.beacon`.

### [P3] cast_receiver/index.html:40 — beacon() drops queued log lines when a POST fails

`beacon()` does `const body = pending.splice(0).join('\n')` (emptying the buffer synchronously), then `fetch(...).catch(() => {})` swallows failures with no re-queue. If the first POST after `beaconUrl` is set fails (proxy socket momentarily unbound, Wi-Fi hiccup, receiver-before-server race), all queued boot diagnostics (device caps, HEVC `canPlayType` results) are lost forever — the exact bring-up data the beacon exists to capture — with no indication. **Fix:** capture `const batch = pending.splice(0)` and `pending.unshift(...batch)` in the `.catch` (with a cap to bound growth) so the next `log()` retries; also flush `pending` the moment `beaconUrl` is assigned rather than waiting for the next `log()`.

### [P3] third_party/.../DiscoveryManagerMethodChannel.kt:275 — categoryForCast() guards null appId but not blank, and the throw precedes any fallback

The `?: DEFAULT_MEDIA_RECEIVER_APPLICATION_ID` substitutes only when `appId` is null. If `setSharedInstance` ever stored an empty/blank string, `categoryForCast("")` throws `IllegalArgumentException`; `selectRoute()` has no try/catch and its caller `startSession()` calls it before `result.success(true)`, so the exception propagates as a `PlatformException` and the connect hangs instead of falling back — defeating the patch's own prefer-real-else-fallback intent. Not reachable today (appId is the hardcoded non-empty `defaultReceiverAppId`), so this is defensive hardening. **Fix:** `val id = CastContextMethodChannel.appId?.takeIf { it.isNotBlank() } ?: DEFAULT_MEDIA_RECEIVER_APPLICATION_ID`, and/or wrap the `categoryForCast(...)` + filter block in a try/catch that falls through to the existing fallbacks.

## What is solid

The core player and cast lifecycle invariants were audited and hold up:

- **Generation guard (`VideoPlayerView`):** the `_generation` counter correctly makes stale async setup bail (`_isStale(gen)` checks on every continuation) so a fast URL/UA switch cannot let an older setup clobber a newer controller. The one nit here (`setState` in `_setUp` running during `initState`) was verified harmless and **rejected** — Flutter permits `setState` during `initState`; there is no assertion to trip.
- **Double-playback fix (`HomeScreen._playerStage`):** gating the local player on `castState.isConnected` with no `AnimatedSwitcher` was confirmed to synchronously unmount `VideoPlayerView` in the same frame a cast starts connecting, so no orphaned better_player controller keeps decoding audio.
- **Honest cast-failure fallback:** the graceful (non-throwing) `_awaitPlaybackStarted` failure path calls `_endSessionQuietly()` → `_stopProxy()` and surfaces an accurate user-facing message ("HEVC / custom User-Agent not supported — still playing on your phone") with a clean local fallback. The lifecycle gaps found (P1s at 130/165) are specifically the *throwing* and *retry* paths that bypass this correct path.
- **Proxy request validation and teardown mechanics:** `_dispatch` reliably converts every thrown handler exception into a 502 (no handler can crash the server), `stop()` wraps `_server.close(force: true)` safely, and `_stopProxy` nulls `_proxy` synchronously before awaiting — so the fire-and-forget teardown in `_onSessionChanged` and the wakelock-ordering concern around it were verified benign and downgraded to P3/rejected. The proxy also correctly binds an OS-assigned ephemeral port with `shared: true`, so there is no fixed-port reuse hazard.
